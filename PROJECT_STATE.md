## Phase 5 — Persistent memory + conversation history (DONE; verified with scripted LLM, not with a live LLM)
Approved choices: memory is written via a tool (no extra extractor LLM call) and limited to exactly five keys.

### Phase 5 limitations (known, not hidden)
- No authentication (Assignment 2): anyone supplying a `student_id` can read/delete that student's memory via the API. Hence only low-risk preferences are stored.
- Screening is rule-based and not exhaustive: unusual phrasings of sensitive data (e.g. a spelled-out number, other languages) can get through, and some harmless text can be refused or redacted (e.g. any message mentioning a rupee amount or the word "bank account" is not stored). Assistant replies containing fee amounts are therefore stored as the redaction placeholder, which weakens follow-up context after fee answers.
- Whether a real LLM calls `remember_preference` appropriately (and only for explicit lasting preferences) is not verified; the code-level validator is the safety net, not the model.
- Memory and history have no expiry/retention limit beyond the 5-key cap and the 6-message context window; old history rows accumulate.

## Phase 7 — Hybrid handbook retrieval fix (DONE; verified with the real local embedder, no live LLM)
**Root cause (inspected):** chunk `s10-1` matched "student visa extension" only through the generic word "student" (neither "visa" nor "extension" appears anywhere in the handbook), yet scored 0.41 semantically; conversely `s5-1` literally contains "re-evaluation of an answer script" but scored only 0.24 because the embedding of a 5-clause chunk dilutes exact terms.
**Change (smallest safe; global threshold NOT simply raised):** `campuspilot/rag.py` now combines semantic similarity with keyword coverage.
- `KeywordScorer`: fraction of the query's information-weighted terms found in a chunk (inverse chunk-frequency weights; query terms absent from the whole handbook still count at maximum weight, which exposes "visa"). Light stemming; two terms match if equal, if the shorter (>=5 letters) is a prefix of the longer, or if they share >=7 leading letters (plagiaris-ing/-m); "elective"/"election" deliberately do NOT match. Generic filler words ("get", "first", "someone"...) are stopwords. A matched term is "distinctive" if it occurs in at most about half the chunks.
- `accept_chunk()` rules (documented in code): accept if (a) similarity >= 0.50 alone ("semantic"); or (b) >= 2 distinctive matched terms, coverage >= 0.60 and similarity >= 0.10 ("keyword", rescues low-similarity exact-term queries); or (c) >= 1 distinctive term, similarity >= 0.40 and coverage >= 0.18 ("semantic+keyword"). Everything else is rejected -> "not found". Chunks are ranked by similarity + coverage; at most `top_k=3` are returned.
- Evidence (and traces) now also carry `keyword_coverage` and `match` (why the chunk was accepted). Settings: `HANDBOOK_MIN_SCORE` (0.40) and new `HANDBOOK_STRONG_SCORE` (0.50). Existing tests that asserted the exact evidence key set were updated for the two new fields (intended); the attendance test now checks that the answering section is among the returned chunks rather than top-1.
- New: `data/retrieval_queries.json` (fictional labelled in/out-of-scope queries, 5 sets) and `scripts/evaluate_retrieval.py` (BEFORE = old rule similarity >= 0.40 only, vs AFTER = hybrid).

**Measured before vs after (real embedder; in-scope answered = an acceptable section among the returned chunks; out-of-scope rejected = nothing returned):**

| Set (in + out queries) | Before in-scope | Before out-scope | After in-scope | After out-scope | Provenance |
|---|---|---|---|---|---|
| design (32+25) | 27/32 | 22/25 | **32/32** | **25/25** | looked at while designing: **in-sample** |
| held-out 1 (12+12) | 10/12 | 10/12 | 10/12 | 11/12 | consumed: one failure type informed tuning |
| held-out 2 (14+13) | 13/14 | 10/13 | 13/14 | 10/13 | consumed: informed `strong_score` 0.55->0.50 |
| held-out 3 (12+12) | 11/12 | 10/12 | 11/12 | 10/12 | consumed: informed the stopword list and the >=2-term rule |
| held-out 4 (12+12) | 10/12 | 7/12 | 10/12 | 7/12 | **pristine: written before the final rule changes, scored once** |

**Honest reading:** the fix removes the reported failure class (generic-word-only matches such as "student visa extension", "student council elections", "student accommodation off campus", and low-similarity exact-term queries such as "re-evaluation of answer script", "change my elective") and caused no measured loss on unseen queries, but the gain on genuinely unseen queries is **zero** (pristine set 4: identical to baseline, 10/12 and 7/12; the individual misses differ). The big design-set improvement is in-sample. During tuning I introduced and then removed two regressions (a 6-letter prefix rule matched "election" to "elective"; one accidental word-form match made "work permit" match section 5). Because sets 1–3 each informed a decision, only set 4 is an unbiased estimate, and it is small (24 queries).
**Known, unfixed limitation (documented as 3 strict `xfail` tests):** *adjacent-topic* questions, where the handbook covers the topic but not the fact asked ("Is smoking allowed in the hostel?", "tuition fee for the whole programme", "Can I bring my pet to the hostel?", "pass mark", "student loans"), share real words and real similarity with a chunk, so no retrieval score separates them from legitimate paraphrases. Rejecting them depends on the LLM obeying the prompt ("answer ONLY from the excerpts; if the excerpt lacks it, say so"), which is **unverified with a live model**. Remaining in-scope misses are vocabulary mismatches ("complaint" vs "grievance", "contest my marks" vs "re-evaluation", "someone else's work" vs "plagiarism"); fixing those needs synonyms or better embeddings.

## Evaluation: pacing, 429 backoff and separation of provider failures (DONE; verified offline/with fakes; NO live run made)
Implements the improvements identified after the first live run (below). No live evaluation was run, `.env` and the real database were not touched (DB rows still 11 / 14 / 0 / 0, `.env` hash unchanged, `reports/` unchanged at 8 files), no key was printed.
- **Provider layer (`campuspilot/provider.py`)**: new policy attributes on every provider (`retry_delays`, `quota_delays`, `max_wait`, `jitter`, `min_interval`, injectable `sleep`/`clock`). *Pacing*: at least `min_interval` seconds between the start of two model requests, retries included (default 0 = off, so the dashboard is unchanged). *429 backoff*: HTTP 429/RESOURCE_EXHAUSTED has its own exponential schedule and counter, separate from 408/5xx/connection errors; each wait is `max(schedule, server hint)` capped at `max_wait`, plus optional jitter; **a server hint larger than `max_wait` makes it give up immediately** (daily quotas). Hints come from the `Retry-After` header (seconds or HTTP date), Google's `RetryInfo.retryDelay` in the error details (also protobuf-style `{seconds, nanos}`), and "retry in 34.5s" in the message; the longest wins; garbage/negative/NaN is ignored. Retries are bounded (1 + len(schedule) attempts per kind). Interactive defaults are unchanged (1 s, 2 s; max 10 s; no pacing). Old `retry_delays=` constructor use still works (one schedule for both kinds; `()` disables). `error_kind()` classifies a failure as `quota` (429) | `unavailable` (408, 5xx, connection/timeout) | `config` (401/403/404) | `request` (other 4xx) | `unknown`; only the first three are "provider-blocked" and **`request`/`unknown` are never excused**. The SDK adds no retries of its own (verified: `retry_options` is None) and has no client timeout (a hung request would wait; Ctrl+C is safe because nothing is written until the end).
- **Agent**: `AgentResult.error_kind` records the classification for `llm_error`s (None on success and for `max_steps_exceeded`).
- **Evaluation (`campuspilot/evaluation.py`)**: every run row has an `outcome`: `completed` | `blocked_by_provider` | `skipped`. A circuit breaker (`stop_after_provider_errors`, CLI `--stop-after`, default 2) skips the remaining turns after N consecutive blocked turns (verified: the provider receives no further requests). `compute_metrics` now reports `runs_completed/blocked/skipped`, `cases_evaluated/blocked`, `provider_error_kinds`, `blocked_runs`, and calculates success rate, case success, tool-choice rate, latency, token availability, citations and agent-error counts **only from completed runs** (a case is evaluable only if all its turns completed; traces are counted over executed runs only). The Markdown report adds a callout, "Runs completed / blocked / not run" rows, BLOCKED/SKIPPED result cells, a "Blocked or not run" list and the pacing used. When nothing was blocked and the report is OFFLINE the text is **byte-for-byte unchanged** (tested by re-rendering the real saved offline report from its saved rows).
- **Legacy reports**: `normalize_report()` derives outcomes at read time for reports saved before this change, from the recorded error text (`llm_error: ClientError 429 …`), flags them `normalized`, and never modifies the file. The pacing used is stored in the report (`meta.pacing`) and shown. New exit code **3 = inconclusive** (provider blocked runs, completed ones passed); 1 = a completed run failed; 2 = no provider; 0 = all passed.
